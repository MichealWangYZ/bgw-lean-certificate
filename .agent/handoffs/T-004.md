**This is a partially weighted local sum in the kernel's internal
dimensionless units. It is not a self-energy, not an energy, and not an error
in any observable.** Missing: `neq(irq)`, `1/ndeg`, `ryd`, the q-sum, and the
separate bare-exchange and static-remainder terms -- all enumerated in the
output's `missing_factors`. And the probe itself is charge-inconsistent and
self-flagged by BerkeleyGW.

Three things a reader could easily get wrong, so they are built into the output
rather than left to prose:

1. **The obvious reference is the wrong one.** Dividing by the 3702 records'
   *own* local contribution gives `205x`. That reference is a tiny subset
   (`3.3e-05`) of the accumulator, so the ratio is meaningless. The output
   carries a `reference_warning` saying so and directs the reader to
   `total_signed_over_affected_accumulators`.
2. **The largest ratio of any kind is `9.356`, and it is an artefact.** Its
   reference accumulator is `-3.7e-06`, four orders below the largest in the
   dataset. The analyser flags any group whose reference is below `1e-3` of the
   maximum (6 groups) and reports the maximum ratio both with and without them.
   The defensible figure is `0.496`.
3. **The effect is concentrated, not spread.** Record 1970 is the `G = G' = 0`
   mode with `wtilde = 21.41492` eV and `|wxt - wtilde| = 6.30e-03` eV, deep
   inside the near-pole window. `branch_mismatch` carries `1/((x-w)(x+w))`, so
   it grows with pole proximity while the recorded contribution stays finite.

## 3. How the accumulator was identified, and a key I got wrong

My first grouping key was `(icalc, band_in, il, iband, ispin, iw, qk)`. It is
**not unique**: the offdiagonal band index `m` is implicit in the `aqsm` array
rather than passed to `mtxel_cor`, and even diagonal calls repeat the tuple
(128 duplicate keys among 384 diagonal accumulator rows). I found this because
the accumulator parser refused a duplicate key rather than silently overwriting.

Rather than guess at a composite key, I added an explicit per-call counter,
incremented once per `mtxel_cor` entry where `iband = sig%diag(il)` is set, and
emitted it in **both** dumps. `(call_id, iw)` is verified unique. The outer
identity is carried alongside and cross-checked for consistency within a call,
so a record assigned to the wrong group is rejected rather than summed.

The accumulator itself is dumped at `Sigma/mtxel_cor.f90:1530-1532`, where
`asxt(iw) = asxt(iw) + asxtemp(iw)`. At that point `asxtemp(iw)` and
`achtemp(iw)` hold the totals over all `n1`, `ig` and `igp` for that call, so
`asxtemp+achtemp` is exactly what the per-record `K*L` sums into. Without this
the headline ratio would have had no valid denominator.

Different `iw` are never summed together: that would add different energy
evaluations of the self-energy.

## 4a. The weight reconstruction is now validated by the source, not trusted

The 0.673% figure rests on my Python reconstruction of the weight
`K = aqsntemp*MYCONJG(aqsmtemp)*vcoul` and the local value
`L = -occ*ssx_post + sch/2`. Nobody had checked that against the code.

The instrumentation now also accumulates `sum(K*L)` over exactly the exported
records **in the Fortran's own arithmetic**, zeroed per `mtxel_cor` call and
emitted as the last accumulator field. Only quantities the code already
computes are summed; the alternative branch expression is never evaluated in
Fortran, as T-004 requires.

| Check | Result |
| --- | --- |
| groups verified | 53 |
| max relative difference, Python vs Fortran | **8.601382692417945e-15** |
| enforced limit in the analyser | `1e-11` |
| totals | agree to `1.385e-16` relative |

The difference is float summation order. The analyser now **fails** if any
group exceeds the limit, and a test confirms a deliberately wrong subtotal is
caught (`test_wrong_reconstruction_is_caught_by_the_fortran_subtotal`) while
one perturbed at `1e-14` is accepted. The three rebuilds this required left
`sigma_hp.log`, both branch-count files and all 3702 records byte-identical.

Also added: `test_iw_range_follows_the_source_fdf_rule`. With the default
`sig%fdf = 2`, `mtxel_cor.f90:514-521` gives `nstart=2, nend=3` for diagonal
calls and `nstart=2, nend=2` for offdiagonal. That predicts `iw in {2,3}`
for the 3336 diagonal records and `iw = 2` for all 366 offdiagonal ones, and
the prediction holds on all 3702. This is why no `iw = 1` record exists.

## 10. Limitations

1. **Not a self-energy.** Missing `neq`, `1/ndeg`, `ryd`, the q-sum, and the
   bare-exchange and static-remainder terms. Dimensionless internal units.
2. **The probe is not physical.** `fermi_level_absolute` below the valence
   maximum; BerkeleyGW reports `RHO` charge `8.00000` against occupations
   giving `7.00000`, and warns the plasma frequency does not track a manual
   Fermi level. It shows no guard prevents the combination, nothing more.
3. **Weights are captured inputs.** `aqsn`, `aqsm`, `vcoul`, `qk` have no
   internal relation in a record and are **not** independently validated.
   Labelled as such in the output.
4. **The comparator is algebra**, not a counterfactual program run.
5. One material, one flavor, one CPU algorithm, `occ = 0.5` only, incremental
   build reusing compiled dependencies -- not a clean-toolchain proof.
6. A physically self-consistent metallic or band-touching witness is still
   missing, still blocked on a real-flavor non-HDF5 metallic asset.
7. The `sigma_cohsex` sign relation from T-003-R2 is reported, not resolved.
8. The 53 groups are the calls containing near-pole `occ != 1` events, not all
   456 accumulator rows; the 0.673% denominator is the affected subset.
