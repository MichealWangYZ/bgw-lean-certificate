## 4. Lean domain-carrying denominator type (Astra)

Integrated from an isolated agent and verified independently in the main tree:
`lake build` clean, **181 theorems** audited (was 126), `AUDIT_MODULE
GW.GPP.PoleDomain` present in the exhaustive audit, only `propext`,
`Classical.choice` and `Quot.sound` in the axiom set, **27** Lean runtime
checks (was 17). The diff is purely additive; the single deleted line in
`scripts/RuntimeChecks.lean` is a trailing comma. No existing theorem was
deleted, weakened or restated.

**The substantive result is a negative one.** The single bundled type Astra
recommended does not work: bundling `x != w` into the type makes the analytic
theorems unstateable, because `continuousAt_occupiedTerm` and
`tendsto_rawOccupied_nhdsWithin_ne` are statements AT `x = w` and need `x` free
to range over a neighbourhood. The shipped design is therefore two levels --
`PoleEnergy` (`w != 0`) for continuity and limits, `AdmissiblePole` adding
`x != +-w` for the algebraic cancellation -- with
`PoleEnergy.eventually_admissible` recording the relation formally.

`Term.check_ok_rawSplitAdmissible_false` is a kernel-checked proof that the
bundle must NOT be used as the evaluator's domain: the evaluator deliberately
accepts the removable pole, and the raw-split domain rejects negative `omega`
that the evaluator accepts. The two domains are provably incomparable in both
directions. That is a real limit on the recommendation, not a workaround.

## 4b. Complex flavor / HDF5 capability scout

Full report: `.agent/handoffs/T-006-CAPABILITY-SCOUT.md` (documentation only;
no repo code changed). I verified its load-bearing claims myself:

**The complex flavor and HDF5 were never the blocker.** Complex flavor is one
preprocessor symbol (`TYPEFLAG = -DCPLX`) with no new dependency. HDF5 needed
no download. I confirmed `/tmp/bgw/t006-complex-hdf5/.../bin/sigma.cplx.x`
exists, is compiled with `-DCPLX` and `-DHDF5`, and is genuinely dynamically
linked against HDF5 (`ldd` shows `libhdf5_fortran.so.320` resolved). So the
capability this project has been treating as the gate for three milestones was
roughly a two-hour build, not a campaign.

**The real blocker is structural and I verified it in the source.**
`MeanField/EPM/epm2bgw.f90:456` is the ONLY assignment to `ifmax`, and it sets
`ifmax(1:numKPoints,1:nspin) = kPoints%numOccupiedBands` -- a single scalar
broadcast across every k-point and spin. `ncrit > 0` requires `ifmax` to VARY
across k-points. Therefore the EPM route cannot produce a partially occupied
conduction band **for any material, ever**. That is a much stronger and more
useful statement than "we lack an asset", and it retroactively explains why the
T-003/T-004 witness had to be manually shifted to be charge-inconsistent: it
was not a shortcut, it was the only thing the EPM route could produce.
GPP additionally requires an `RHO` file (`Sigma/input.f90:872`).

**A T-003 claim is overturned.** T-003 recorded that a real-flavor, non-HDF5
band-touching asset was missing. `testsuite/Graphene` is one: I confirmed
`PARATEC_graphene.tar.xz` ships `RHO`, `WFN_co`, `WFN_fi` and `vxc.dat`. The
original grep missed it because `screening_metal` is injected at runtime by
`sed` at `Graphene.test:103` rather than appearing in any committed input. The
asset is nonetheless not sufficient: its k-grids do not contain the Dirac
point, and the run reports `Number of partially occ. conduction bands: 0`.

So what is missing is **a new mean-field calculation**, not a flavor, a
library, or a toolchain. No DFT code is present on this machine and obtaining
one is network-dependent, so that thread was stopped per the constraint.

**Two cautions I am carrying forward, not burying.**
1. The HDF5 `arch.mk` points into an unrelated project's conda env which
   contains a truncated `libgfortran.so.5.0.0`. It must NOT be promoted to
   durable provenance, and `PROVENANCE-R6.txt` deliberately does not vouch for
   any `t006-*` binary.
2. Toolchain drift: `docs/` records gfortran 13; the environment now has
   16.2.0. `bgw/reproduce.py` was not rerun, so **no claim is made** that the
   archived byte-exact Si-EPM reproduction still holds under gfortran 16. That
   is an open question, not a known-good.

The scout's recommended next step (an EPM `"El"` free-electron witness with a
symmetry-protected band touching) is a PROPOSAL only. It is not implemented and
I am not authorized to choose it: it would be better than the current
manually-shifted witness and worse than real graphene-at-K, and jellium is not
a material. That trade-off is the owner's call.

## 5. Band-index symmetry and the cutoff-sensitivity curve

New, additive: `bgw/weighted_audit/symmetry_audit.py`,
`bgw/weighted_audit/cutoff_sweep.py`, `tests/test_symmetry_audit.py` (18),
`tests/test_cutoff_sweep.py` (15). No existing file was edited by that agent.

**Symmetry: NOT TESTABLE on this dataset, and the usual diagnosis is wrong.**
Real flavor means the relation is plain symmetry `Sigma_nm = Sigma_mn`, read
from `mtxel_cor.f90:14-24,1710-1717`, not conjugate symmetry. The packet's note
that the ket band `m` is not exported is true but is NOT the blocker: `m` is
recoverable by fingerprinting `aqsm` against the diagonal calls' bit-exact
values, and the recovered pair set `{(1,1),(1,8),(2,1)}` reproduces the
`sigma.inp` offdiag block exactly. The real blocker is that BerkeleyGW never
computed the transposes `(8,1)` and `(1,2)` -- they are not in the input, so
there is no second quantity to compare. Fixing it needs a different run
(`sigma_matrix <loff> 0`), not another export field. I re-ran the module and
confirmed the verdict and the pair table.

A separate `(G,G')` antisymmetry measurement is included (3568 transposed pairs
+ 120 unpaired + 14 diagonal = 3702, complete) and is explicitly flagged as NOT
the band-index test: the antisymmetric part is contracted with
`M_n(G) M_m(G')` and cancels identically when `n == m`, and it is measured on
the near-pole subset only. It must not be quoted as evidence about Hermiticity.

**Cutoff sweep: 49.6% is a plateau, not a threshold artefact.** I re-ran this
myself and reproduced the table exactly. `0.495974` is the reported maximum for
every relative cutoff in `(1.919051e-4, 1.457943e-1]`, with the same argmax
group (call 107, `iw=2`, diagonal, band 8, 134 events, accumulator `-0.02903`)
throughout. The module enumerates the exact breakpoints rather than only
sampling a grid. The shipped `1e-3` is interior to that plateau, 0.72 decades
above its lower edge and 2.16 decades below its upper edge.

This is a robustness property of a REPORTING CHOICE, not a physical fact. Every
caveat in packet section 4 applies unchanged: intermediate Rydberg units,
stripped outer factors differing by output type, a charge-inconsistent probe,
and `(call_id, iw)` as a grouping chosen for this diagnostic.

## 6. Failed attempts, and things I or an agent got wrong

1. **An agent overstated a result and I caught it by recomputing.** The
   cutoff-sweep agent reported that the shipped `1e-3` "sits roughly in the
   geometric middle" of the plateau. It does not: the geometric midpoint is
   `5.29e-3`, and `1e-3` sits at the **25th percentile** of the plateau in log
   space. The substantive point (it is comfortably interior, not near an edge)
   survives; the characterisation does not. The overstatement was only in the
   agent's report to me and never entered the committed code, which I verified
   by grepping for it. Recorded because an unverified agent summary is exactly
   how a wrong claim would enter this project.
2. **I put `summarise_groups` after the `__main__` guard.** The extraction
   placed the new function below `raise SystemExit(main())`, so it was not
   defined when `main` ran and the CLI died with `NameError`. Caught by running
   the CLI rather than only the unit tests.
3. **The module split broke three contract tests, correctly.**
   `CompletenessSourceCommentTests` read `wm.__file__` and split on
   `"EXPECTED_RECORDS = "`, which had moved to `contract.py`. Rather than
   hard-code the new filename I resolve it through the constant's own module
   and assert the marker is present, so a future move cannot leave the test
   reading the wrong file and passing vacuously. Relatedly,
   `test_source_comments_carry_no_rejected_wording` scanned one file; after a
   split into four, that would leave three unscanned, so it now scans every
   module in the package and asserts it found at least four.
4. **The manifest went stale again -- the sixth time in this project.** I
   generated `PROVENANCE-R6.txt`, then edited `REVIEW_PACKET.md` and
   `tests/test_review_packet.py` to roll them from R5 to R6, which invalidated
   the digests I had just written. The "generate the manifest strictly last"
   rule is not enough on its own, because rolling the manifest revision is
   itself an edit to files the manifest covers -- the rule has a built-in
   circularity that has now bitten six times. The durable fix is to make
   manifest generation a rerunnable step rather than a one-shot act performed
   at the right moment.

   It then happened an **eighth** time, perfectly circularly: writing the note
   you are reading invalidated the digests again. So I stopped hand-patching
   and built `scripts/make_manifest.py`, which re-hashes every path a manifest
   ALREADY lists, in place, idempotently. It never adds or removes an entry, so
   deciding what a manifest vouches for stays a human act; only the digests are
   mechanical. Run it as many times as needed until the tree settles.

   **The first version of that script silently did nothing.** I omitted
   `re.MULTILINE`, so `^`/`$` anchored to the whole string, no line matched,
   and it printed "0 refreshed, 0 missing" as if that were success -- a silent
   pass, in the tool written to stop silent passes. It now refuses to report
   success when zero digest lines match, and prints the number of entries
   scanned so "0 refreshed" can be distinguished from "0 seen".
5. **The gate partition guard caught the integration, not me.** I copied in the
   two new test modules and the suite failed on `test_every_module_is_classified`
   before I had classified them. That is the guard working on its first real
   encounter, but it is also me forgetting the step I had just built.
