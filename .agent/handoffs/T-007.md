## 0. The findings were verified before anything was changed

All three were reproduced against `374459f` from first principles, not taken
from the report:

| # | Claim | Independent check | Verdict |
| --- | --- | --- | --- |
| F1 | non-finite input reports zero error | `max(0.0, nan)` is `0.0`; `abs(nan - 1.0) > 0` is `False` | **real** -- a NaN both passes the delta check AND vanishes from the maximum |
| F2 | the oracle is data-supplied | `bgw/branch_boundary/branch_boundary.f90:331` writes a `closed_form` column; `analyze.py:310` compared against that column | **real** |
| F3 | coverage is OCCCHK-driven | `analyze.py:296` loops over OCCCHK, not a validated OCC inventory | **real** |

The audit's own eight tests ran 5 failures / 3 passes on the base, exactly as
its report stated.

**F2 was sharper than the report's summary suggests.** An independent oracle
already existed in the same file -- `analyze.py:88` `closed_form()` recomputes
from `occ, ieps, wt, wxt`. It was simply wired to the wrong place: used in the
detail dump at `:238`, not in the error metric at `:310`. The fix was to use
the function that was already there.

## 1. Repairs

* **F1** -- `parse_text` now rejects any non-finite numeric field at the parser
  boundary, naming the row tag and column. Derived metrics (`spread`,
  `rel_closed`, `rel_supplied`) are validated finite before being returned, and
  CLI emission uses `allow_nan=False` as a last guard. A future row type that
  legitimately needs a non-finite diagnostic must opt in with an explicit
  status rather than arrive as a silent NaN.
* **F2** -- `occupation_report` recomputes the expectation with `closed_form()`
  from the physical inputs and compares `delta` against that. The driver's own
  column is still checked, but as an OUTPUT under test, reported separately as
  `supplied_closed_form_error`. Also added: `ieps`, `wt` and `wxt` must be
  constant across a point's occupation sweep, since otherwise it is not a
  linearity test at all (the report's second F2 probe).
* **F3** -- OCC and OCCCHK must describe the same point set, OCCCHK must have
  exactly one row per point, and `(point, occ)` must be unique.

## 2. No T-005 number moved

Checked explicitly, before and after, on `artifacts/t005/raw_sweep.txt`:

* the real data contains **zero** non-finite values, so the parser rejection
  cannot affect it;
* the driver's supplied `closed_form` column agrees with the independent
  recomputation to **exactly 0.0** relative difference, so switching the oracle
  changes no metric;
* a full diff of `summarize()` output against the pre-repair baseline shows
  **one** difference: the new `supplied_closed_form_error` field, which reads
  `0.0` at all four points. Every pre-existing value is identical.

So the repair is behaviour-preserving on real data and only bites on
adversarial data. This supports the audit's own careful statement: nothing here
shows the T-005 measurements were wrong. What was wrong is that the checker
would not have noticed if they were.
